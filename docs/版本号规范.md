# 版本号规范（Versioning Standard）

> 适用范围：IPlay-Compression 项目（Nuxt 前端应用）及所有遵循语义化版本管理的代码、依赖与发布流程。
> 当前版本：`1.0.0`（见 `package.json`）

---

## 1. 总览

本项目采用 **语义化版本 2.0.0（Semantic Versioning 2.0.0，简称 SemVer）** 作为统一的版本号行业标准。

版本号固定由 **三段数字** 组成，格式为：

```
主版本号.次版本号.修订号
   X       . Y       . Z
```

- 每段均为非负整数，禁止前导零（如 `01` 不合法，`1` 合法）。
- 每段数字按十进制递增，递增量无上限。
- 版本号之间用半角点号 `.` 分隔。

完整扩展格式（含可选后缀）：

```
主版本号.次版本号.修订号-预发布标识+构建元数据
    X       . Y       . Z       -alpha+20260926
```

---

## 2. 三段数字的含义

| 字段 | 名称 | 含义 | 递增触发条件 |
| --- | --- | --- | --- |
| `X` | 主版本号（MAJOR） | 不兼容的 API / 重大架构变更 | 做了任何**向后不兼容**的修改 |
| `Y` | 次版本号（MINOR） | 向下兼容的新功能 | 以**向后兼容**的方式新增了功能 |
| `Z` | 修订号（PATCH） | 向下兼容的问题修复 | 做了**向后兼容**的缺陷修复 |

**核心原则**：一旦某一段递增，其右侧所有段必须归零。

- 升级主版本：`1.4.7` → `2.0.0`
- 升级次版本：`1.4.7` → `1.5.0`
- 升级修订号：`1.4.7` → `1.4.8`

---

## 3. 版本升级决策流程

```
发生了变更？
  ├─ 是否向后不兼容（破坏性变更）？
  │     └─ 是 → MAJOR +1，MINOR=0，PATCH=0
  │
  ├─ 是否新增功能（向后兼容）？
  │     └─ 是 → MINOR +1，PATCH=0
  │
  └─ 是否仅修复缺陷 / 微调（向后兼容）？
        └─ 是 → PATCH +1
```

---

## 4. 预发布版本（Pre-release）

在正式发布前，可通过追加连字符 `-` 与标识符标记预发布版本：

```
1.1.0-alpha
1.1.0-alpha.1
1.1.0-beta.2
1.1.0-rc.1
```

- 预发布标识符由点分隔的字母数字与连字符组成（`[0-9A-Za-z-]`）。
- **优先级低于对应的正式版本**：`1.1.0-alpha < 1.1.0`。
- 建议的内部阶段约定：

| 标识 | 含义 | 使用场景 |
| --- | --- | --- |
| `alpha` | 内测 / 功能未完成 | 开发自测、内部演示 |
| `beta` | 公测 / 功能冻结 | 邀请用户体验 |
| `rc` | 候选发布 | 待最终验证后转正式 |

示例：`1.2.0-beta.1` 表示 1.2.0 的第二个公测版本。

---

## 5. 构建元数据（Build Metadata）

以加号 `+` 追加，仅供信息记录，不影响版本优先级：

```
1.1.0+20260926
1.1.0-beta.1+build.042
```

常见包含：构建时间、提交哈希（commit hash）、CI 流水号。

---

## 6. 本项目应用约定

结合 `package.json` 现状，明确本项目实践规则：

1. **正式发布**：始终保持 `X.Y.Z` 三段格式，如当前 `1.1.0`。
2. **依赖版本**：`dependencies` 中允许使用 `^`（兼容更新）与 `~`（补丁更新），但**项目自身 `version` 字段必须为精确三段式**，不得带 `^`、`~` 等符号。
3. **Git Tag**：每次正式发版必须打对应标签，格式与版本号一致：
   ```
   git tag v1.1.0
   git tag v2.0.0
   ```
4. **首个正式版**：从 `1.0.0` 起算；`0.x.x` 表示开发阶段（API 尚未稳定）。
5. **破坏性变更公告**：MAJOR 升级须在 `README` / 变更日志（CHANGELOG）中说明迁移影响。

### 示例：本项目合理的迭代路径

```
1.0.0  初始正式版（MVP，见 docs/v1.0.0迭代（MVP）.md）
1.0.1  修复压缩参数导致的边界崩溃
1.1.0  新增批量压缩功能（向下兼容）
2.0.0  重构压缩内核 API，移除旧接口
```

---

## 7. 版本比较规则（优先级）

从高到低比较，依次比对 `MAJOR → MINOR → PATCH → 预发布标识`：

1. 数字段按数值比较（非字符串）。
2. 有预发布标识的版本 **低于** 无预发布标识的同号版本。
3. 预发布标识之间按字典序 + 数字数值规则比较（`1.1.0-alpha < 1.1.0-alpha.1 < 1.1.0-beta`）。
4. 构建元数据 **不参与** 优先级比较。

---

## 8. 禁止事项

- ❌ 前导零：`1.01.0` 非法。
- ❌ 缺段：`1.1`、`1` 非法（项目自身版本必须三段齐全）。
- ❌ 项目 `version` 字段带范围符号（`^1.1.0`、`~1.1.0`）。
- ❌ 在修订号段里塞入非数字（如 `1.1.0-fix`），应使用预发布标识而非污染修订号。
